## My Reflection

ตลอดกระบวนการเริ่มต้นใน **Lab 4 (TokTickIT Actions Taken, Dashboards, and Final Regression)** โดยเฉพาะในขั้นตอนการจัดทำ **Sprint 4 Engineering Contract (Issue #55 / PR #66)**, **Test DD Blueprint & Traceability Plan (Issue #56 / PR #67)**, **Database Migration & Seed Foundation (Issue #57)**, **Actions Taken REST APIs & Authorization (Issue #58)**, และ **Actions Taken UI on Ticket Detail (Issue #59)** ผมได้เรียนรู้และสะท้อนบทเรียนสำคัญทางวิศวกรรมซอฟต์แวร์ดังนี้:

1. **บทบาทของมนุษย์ในฐานะ Lead Architect ในการกำกับและคัดกรอง AI:**
   การใช้ AI Agent ในการร่างข้อกำหนดช่วยลดเวลาในการพิมพ์ boilerplate ได้อย่างมาก แต่สิ่งที่สำคัญที่สุดคือ **การเป็นผู้กำกับเชิงตรรกะและโครงสร้าง (Architectural Oversight)** ในรอบแรกสุด AI มักจะสรุปและจัดกลุ่มงานตามตัวอย่างในเอกสารอย่างกว้าง ๆ (เช่น ยุบงานทั้งหมดเหลือเพียง 6 ก้อนใหญ่) ซึ่งหากปล่อยให้ทำต่อจะทำให้ Pull Request แต่ละอันมีขนาดใหญ่เกินไป (Bloated PRs) และตรวจทานได้ยาก ผมจึงต้องเข้ามาแทรกแซงและสั่งจัดโครงสร้างใหม่ให้แยกเป็น **11 Granular Issues** ที่สะท้อนตามเกณฑ์การให้คะแนนจริง (แยก Spec DD, Test DD, DB Migration, APIs, UI, Workflow, Dashboards, Visual QA และ E2E ออกจากกัน) เพื่อให้การพัฒนาเป็นไปอย่างราบรื่นและมี PR ขนาดเล็กที่ตรวจสอบได้ง่าย

2. **ความสำคัญของการแยก Spec DD ออกจาก Test DD ก่อนลงมือเขียนโค้ด:**
   ในกระบวนการ Test-Driven Development (TDD) ข้อผิดพลาดที่พบบ่อยคือการรวมการเขียน Test Plan เข้าไปใน Specification โดยตรง แต่ในทางวิศวกรรมจริง การมี Specification ที่นิ่งและได้รับการอนุมัติ (Approved Contract) ก่อน แล้วจึงนำข้อกำหนดเหล่านั้นมาแตกเป็น **Acceptance Criteria Traceability Matrix** ใน `tests.md` จะช่วยให้เรามองเห็นภาพรวมของชุดทดสอบที่จำเป็นต้องมีครบทุกมิติ (ครอบคลุมทั้ง 10 ประเภทตามที่อาจารย์กำหนดใน Section 10) การที่ระบบมี Test IDs ที่เจาะจงล่วงหน้าก่อนลงมือเขียนโค้ด ทำให้ทีมพัฒนาสามารถใช้ Test IDs เหล่านี้เป็นเป้าหมายที่วัดผลได้อย่างชัดเจน

3. **คุณค่าของการรับฟังและปรับปรุงตาม Peer Review ของคู่ตรวจ:**
   ในการรีวิว **PR #67** โดยเพื่อนคู่ตรวจ (@thanapornboont-star) ได้ให้ข้อคิดเห็นที่เฉียบคมและตรงประเด็นมาก โดยชี้ให้เห็นว่าในร่างแรกของ `tests.md` ยังขาดชุดทดสอบประเภท **Performance-Smoke Tests** และการแยกแยะระหว่าง **UI Component กับ UI Style/Responsive Tests** ให้เด่นชัด รวมถึงการใช้คำว่า "100%" ที่อาจทำให้ผู้อ่านเข้าใจผิดว่าเป็นผลการรันเทสต์ที่ผ่านแล้ว ทั้งที่เป็นเอกสารแผนงานก่อนเริ่มทำโค้ด ผมได้นำคอมเมนต์ดังกล่าวมาปรับแก้ทันที โดยเพิ่มการทดสอบความเร็วในการตอบสนองของ Dashboard API (`SMOKE-01`), ความเร็วในการโหลดรายการ Actions Taken (`SMOKE-02`), และปรับแก้ข้อความให้สื่อชัดเจนว่าเป็น **100% Planned Requirements Coverage** สิ่งนี้สะท้อนให้เห็นว่าการมีกระบวนการ Peer Review ที่จริงจังและข้อความจริงคำต่อคำช่วยยกระดับคุณภาพของเอกสารสัญญาให้รัดกุมและถูกต้องตามหลักวิศวกรรมอย่างแท้จริง

4. **การเตรียมพร้อมรับมือกับ Edge Cases ของ Resolution Gate และ Concurrency:**
   การวิเคราะห์เงื่อนไขทางธุรกิจใน Specification ทำให้เราตระหนักว่าจุดเสี่ยงสำคัญของ Lab 4 คือเรื่อง **Resolution Gate (ห้าม Resolve ตั๋วถ้าไม่มี Actions Taken อย่างน้อย 1 รายการ)** และการแยกระหว่างการกด Problem Appears Resolved ของผู้ใช้กับการเปลี่ยนสถานะจริง การวางแผน Test Cases ดักจับเคสเหล่านี้ล่วงหน้า (`WF-01` ถึง `WF-05`) จะทำให้ในขั้นตอนเขียนโค้ดถัดไป (Issue #57–60) เราสามารถสร้างโค้ดที่ผ่านเงื่อนไขความปลอดภัยและไม่มีช่องโหว่ได้อย่างแน่นอน

5. **การทำ Non-destructive Database Migration และ Idempotent Seed:**
   ในขั้นตอนของ **Issue #57** การเพิ่มเอนทิตีลูก `ActionTaken` เข้าสู่ระบบที่มีตารางเดิมจาก Lab 1–3 ต้องการความรอบคอบอย่างสูงเพื่อรักษาหลักการ **Zero Data Loss** ผมได้ตรวจสอบไฟล์ `migration.sql` อย่างละเอียดเพื่อให้แน่ใจว่าไม่มีคำสั่ง `DROP` หรือการลบคอลัมน์เดิมใด ๆ และในส่วนของ `seed.ts` ได้วางโครงสร้างให้เช็คจำนวนเรคอร์ดเดิมก่อนสร้างเสมอ เพื่อให้สามารถรันซ้ำกี่ครั้งก็ได้โดยไม่เกิด duplicate key หรือข้อมูลบวม การเขียนเทสต์ `MIG-01`, `MIG-02`, และ `SEED-01` รองรับทันทีช่วยยืนยันว่าสัญญาระดับฐานข้อมูลถูกบังคับใช้อย่างสมบูรณ์และผ่าน 100% ก่อนจะเริ่มต่อเติม REST API ในขั้นตอนถัดไป

6. **Server-Side Authorization Boundaries, Zero-Leakage Privacy, และ Optimistic Concurrency Control:**
   ในขั้นตอนของ **Issue #58** การพัฒนา REST API สำหรับ Actions Taken ต้องคำนึงถึงความปลอดภัยของข้อมูลเป็นหัวใจหลัก:
   - **Zero Leakage & Isolation:** ฝั่ง Requester ได้รับอนุญาตให้ดู Actions Taken ได้เฉพาะตั๋วที่ตนเองเป็นเจ้าของเท่านั้น (`ticket.requesterId === req.user.id`) และหากเข้าถึงตั๋วของผู้อื่น ระบบจะส่งกลับ `404 Not Found` แทนที่จะเป็น `403 Forbidden` เพื่อป้องกันการสำรวจการมีอยู่ของตั๋วในระบบ (Enumeration Attack)
   - **Automatic Performer Attribution:** เพื่อป้องกันการปลอมแปลงชื่อผู้ปฏิบัติงาน ระบบล็อก `performedById` จาก Authenticated Session เท่านั้น ไม่รับค่าจาก Client Payload
   - **Optimistic Concurrency Control:** เพื่อรองรับการแก้ไขข้อมูลพร้อมกันหลายคน ระบบตรวจสอบ `expectedUpdatedAt` หากข้อมูลบนเซิร์ฟเวอร์ถูกเปลี่ยนแปลงไปก่อนหน้า จะส่ง `409 Conflict` พร้อมคืน `currentUpdatedAt` ให้ฝั่งหน้าบ้านจัดการเตือนผู้ใช้ได้อย่างปลอดภัย
   การเขียน Automated Tests ครอบคลุมทั้ง 22 เคส (`actions-taken.api.test.ts`) ส่งผลให้มั่นใจได้ว่า API ทำงานอย่างถูกต้องและปลอดภัย 100% ปราศจาก regression ใดๆ ต่อระบบเดิม

7. **การออกแบบ Parent-Child UI และการรักษาสมดุลระหว่าง Accessibility กับ Regression Safety:**
   ในขั้นตอนของ **Issue #59** การนำคอมโพเนนต์ `ActionsTaken` เข้ามาผูกกับ `StaffTicketDetail` เป็นตัวอย่างที่ดีของการผสานระบบงานแบบ Parent-Child (Ticket ➔ Actions Taken):
   - **User-Centric & Accessible Form Design:** การทำ Modal Dialog สำหรับ Log/Edit Action ต้องปฏิบัติตามมาตรฐาน Accessibility (`role="dialog"`, `aria-modal="true"`, focus management, escape key) และมี inline validation ที่ชัดเจน โดยเฉพาะกฎ **BR-07** ที่บังคับ `followUpNote` เฉพาะเมื่อมีการติ๊กเลือกการติดตาม
   - **Automatic Provenance & Immutable Attribution:** การล็อกช่อง `performedBy` ให้แสดงชื่อและบทบาทของผู้ล็อกอินปัจจุบันในแบบ Read-only ช่วยให้มั่นใจได้ว่าข้อมูลการบันทึกงานสอดคล้องกับ Session ทางเทคนิค
   - **Regression Awareness:** การตรวจจับความสัมพันธ์ระหว่างสัญญางานเดิมของ Lab 2 (ซึ่งมีเทสต์ดักว่าหน้า RequesterTicketDetail ต้องไม่มีคำว่า actions taken ในขณะนั้น) ทำให้เราต้องระมัดระวังไม่แทรก element ที่ไปขัดแย้งกับ regression suite เดิม ส่งผลให้สามารถรักษาอัตราการผ่านของเทสต์ได้ 100% ทั้ง 288 การทดสอบอย่างสมบูรณ์แบบ
