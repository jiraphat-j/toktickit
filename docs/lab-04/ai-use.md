   ในกระบวนการ Test-Driven Development (TDD) ข้อผิดพลาดที่พบบ่อยคือการรวมการเขียน Test Plan เข้าไปใน Specification โดยตรง แต่ในทางวิศวกรรมจริง การมี Specification ที่นิ่งและได้รับการอนุมัติ (Approved Contract) ก่อน แล้วจึงนำข้อกำหนดเหล่านั้นมาแตกเป็น **Acceptance Criteria Traceability Matrix** ใน `tests.md` จะช่วยให้เรามองเห็นภาพรวมของชุดทดสอบที่จำเป็นต้องมีครบทุกมิติ (ครอบคลุมทั้ง 10 ประเภทตามที่อาจารย์กำหนดใน Section 10) การที่ระบบมี Test IDs ที่เจาะจงล่วงหน้าก่อนลงมือเขียนโค้ด ทำให้ทีมพัฒนาสามารถใช้ Test IDs เหล่านี้เป็นเป้าหมายที่วัดผลได้อย่างชัดเจน

3. **คุณค่าของการรับฟังและปรับปรุงตาม Peer Review ของคู่ตรวจ:**

4. **การเตรียมพร้อมรับมือกับ Edge Cases ของ Resolution Gate และ Concurrency:**
   การวิเคราะห์เงื่อนไขทางธุรกิจใน Specification ทำให้เราตระหนักว่าจุดเสี่ยงสำคัญของ Lab 4 คือเรื่อง **Resolution Gate (ห้าม Resolve ตั๋วถ้าไม่มี Actions Taken อย่างน้อย 1 รายการ)** และการแยกระหว่างการกด Problem Appears Resolved ของผู้ใช้กับการเปลี่ยนสถานะจริง การวางแผน Test Cases ดักจับเคสเหล่านี้ล่วงหน้า (`WF-01` ถึง `WF-05`) จะทำให้ในขั้นตอนเขียนโค้ดถัดไป (Issue #57–60) เราสามารถสร้างโค้ดที่ผ่านเงื่อนไขความปลอดภัยและไม่มีช่องโหว่ได้อย่างแน่นอน

5. **การทำ Non-destructive Database Migration และ Idempotent Seed:**
   ในขั้นตอนของ **Issue #57** การเพิ่มเอนทิตีลูก `ActionTaken` เข้าสู่ระบบที่มีตารางเดิมจาก Lab 1–3 ต้องการความรอบคอบอย่างสูงเพื่อรักษาหลักการ **Zero Data Loss** ผมได้ตรวจสอบไฟล์ `migration.sql` อย่างละเอียดเพื่อให้แน่ใจว่าไม่มีคำสั่ง `DROP` หรือการลบคอลัมน์เดิมใด ๆ และในส่วนของ `seed.ts` ได้วางโครงสร้างให้เช็คจำนวนเรคอร์ดเดิมก่อนสร้างเสมอ เพื่อให้สามารถรันซ้ำกี่ครั้งก็ได้โดยไม่เกิด duplicate key หรือข้อมูลบวม การเขียนเทสต์ `MIG-01`, `MIG-02`, และ `SEED-01` รองรับทันทีช่วยยืนยันว่าสัญญาระดับฐานข้อมูลถูกบังคับใช้อย่างสมบูรณ์และผ่าน 100% ก่อนจะเริ่มต่อเติม REST API ในขั้นตอนถัดไป

6. **Server-Side Authorization Boundaries, Zero-Leakage Privacy, และ Optimistic Concurrency Control:**
   ในขั้นตอนของ **Issue #58** การพัฒนา REST API สำหรับ Actions Taken ต้องคำนึงถึงความปลอดภัยของข้อมูลเป็นหัวใจหลัก:
   - **Zero Leakage & Isolation:** ฝั่ง Requester ได้รับอนุญาตให้ดู Actions Taken ได้เฉพาะตั๋วที่ตนเองเป็นเจ้าของเท่านั้น (`ticket.requesterId === req.user.id`) และหากเข้าถึงตั๋วของผู้อื่น ระบบจะส่งกลับ `404 Not Found` แทนที่จะเป็น `403 Forbidden` เพื่อป้องกันการสำรวจการมีอยู่ของตั๋วในระบบ (Enumeration Attack)
   - **Automatic Performer Attribution:** เพื่อป้องกันการปลอมแปลงชื่อผู้ปฏิบัติงาน ระบบล็อก `performedById` จาก Authenticated Session เท่านั้น ไม่รับค่าจาก Client Payload
   - **Optimistic Concurrency Control:** เพื่อรองรับการแก้ไขข้อมูลพร้อมกันหลายคน ระบบตรวจสอบ `expectedUpdatedAt` หากข้อมูลบนเซิร์ฟเวอร์ถูกเปลี่ยนแปลงไปก่อนหน้า จะส่ง `409 Conflict` พร้อมคืน `currentUpdatedAt` ให้ฝั่งหน้าบ้านจัดการเตือนผู้ใช้ได้อย่างปลอดภัย
   การเขียน Automated Tests ครอบคลุมทั้ง 22 เคส (`actions-taken.api.test.ts`) ส่งผลให้มั่นใจได้ว่า API ทำงานอย่างถูกต้องและปลอดภัย 100% ปราศจาก regression ใดๆ ต่อระบบเดิม

7. **การออกแบบ Parent-Child UI และการรักษาสมดุลระหว่าง Accessibility กับ Regression Safety:**
   ในขั้นตอนของ **Issue #59** การนำคอมโพเนนต์ `ActionsTaken` เข้ามาผูกกับ `StaffTicketDetail` เป็นตัวอย่างที่ดีของการผสานระบบงานแบบ Parent-Child (Ticket ➔ Actions Taken):
   - **User-Centric & Accessible Form Design:** การทำ Modal Dialog สำหรับ Log/Edit Action ต้องปฏิบัติตามมาตรฐาน Accessibility (`role="dialog"`, `aria-modal="true"`, focus management, escape key) และมี inline validation ที่ชัดเจน โดยเฉพาะกฎ **BR-07** ที่บังคับ `followUpNote` เฉพาะเมื่อมีการติ๊กเลือกการติดตาม
   - **Automatic Provenance & Immutable Attribution:** การล็อกช่อง `performedBy` ให้แสดงชื่อและบทบาทของผู้ล็อกอินปัจจุบันในแบบ Read-only ช่วยให้มั่นใจได้ว่าข้อมูลการบันทึกงานสอดคล้องกับ Session ทางเทคนิค
   - **Regression Awareness:** การตรวจจับความสัมพันธ์ระหว่างสัญญางานเดิมของ Lab 2 (ซึ่งมีเทสต์ดักว่าหน้า RequesterTicketDetail ต้องไม่มีคำว่า actions taken ในขณะนั้น) ทำให้เราต้องระมัดระวังไม่แทรก element ที่ไปขัดแย้งกับ regression suite เดิม ส่งผลให้สามารถรักษาอัตราการผ่านของเทสต์ได้ 100% ทั้ง 288 การทดสอบอย่างสมบูรณ์แบบ

8. **ความสำคัญของ Resolution Gate และ State Machine Enforcement ในฝั่งเซิร์ฟเวอร์:**
   ในขั้นตอนของ **Issue #60** จุดสำคัญคือการตระหนักว่าการควบคุมบน UI (เช่น การ disable ปุ่ม หรือแสดงกล่องเตือนสีเหลืองอำพัน) เป็นเพียง **User Experience Guidance** เท่านั้น แต่ **อำนาจในการตัดสินใจและการบังคับใช้กฎทางธุรกิจ (Business Rules Authority)** จะต้องอยู่ที่ฝั่ง Backend Server 100%:
   - **Resolution Gate Server Enforcement (BR-13, AC-06):** เซิร์ฟเวอร์ต้อง query นับจำนวน `ActionTaken` ของตั๋วนั้นโดยตรง หากเท่ากับ 0 ต้อง reject ด้วย `400 Bad Request (RESOLUTION_GATE_FAILED)` เสมอ แม้ Client จะพยายามยิง request ตรงเข้ามาก็ตาม
   - **Advisory vs Deterministic Action (BR-14, AC-08):** การที่ Requester กด "Problem Appears Resolved" เป็นเพียงสัญญาณบอกผู้ปฏิบัติงาน ไม่สามารถเปลี่ยนสถานะตั๋วเป็น RESOLVED ได้โดยอัตโนมัติ เพื่อป้องกันการปิดงานโดยที่ยังไม่มีการบันทึกการกระทำจริง
   - **State Transition Matrix Completeness (BR-15):** การกำหนด transition matrix ให้รัดกุมพร้อมป้องกัน illegal jump (เช่น NEW ข้ามไป RESOLVED ตรงๆ) ช่วยรักษา integrity ของ workflow ตลอดวงจรชีวิตของตั๋ว

9. **Operational Dashboards: การรักษาสมดุลระหว่าง Summary Analytics กับ Detailed Operations (Issue #61):**
   ในขั้นตอนของ **Issue #61** การออกแบบและสร้าง IT Staff Operational Dashboard สะท้อนหัวใจสำคัญของแดชบอร์ดระดับองค์กร:
   - **Summary without Replacing Detailed Views:** แดชบอร์ดต้องไม่ใช่หน้าจอที่มาแทนที่ Ticket Queue หรือ Ticket Detail แต่ทำหน้าที่เป็น **Operational Command Center** ที่สรุปตัวชี้วัดสำคัญ (Unassigned, My Tickets, High Priority, Personal Actions) และเปิดโอกาสให้ผู้ใช้งานคลิก **Interactive Drill-Down** ไปยังคิวงานหรือตั๋วที่ต้องจัดการได้ทันที
   - **Strict Data Scoping & Personal Contribution:** ตัวชี้วัดภาระงานส่วนบุคคล (`myActionsCount` และ `myRecentActions`) ต้องถูกกักกันสิทธิ์ (User-Scoped) ให้อิงจาก Authenticated Session เสมอ เพื่อแสดงประวัติการทำงานจริงของเจ้าหน้าที่คนนั้นอย่างแม่นยำและไม่ปะปนกับผู้อื่น
   - **Performance Smoke Latency:** เพื่อให้แดชบอร์ดตอบสนองได้รวดเร็วตามสัญญาทางวิศวกรรม (`SMOKE-01` < 200ms) โครงสร้างการ Query ใช้ Prisma aggregations และดึงเฉพาะ Top 10 Active Tickets และ Top 5 Recent Actions ส่งผลให้เวลาในการประมวลผลอยู่ต่ำกว่า 200ms อย่างสม่ำเสมอ
   - **Zero Regression Full-Stack Continuity:** การเพิ่มแดชบอร์ดเข้ามาใน Navigation Shell ทั้งฝั่ง `AppHeader` และ `App.tsx` ได้รับการทดสอบร่วมกับ Test Suites เดิมของ Lab 1–3 ทำให้มั่นใจได้ว่าฟังก์ชันการทำงานเดิมทั้ง 319 การทดสอบยังคงผ่าน 100% โดยสมบูรณ์

10. **Requester Role Dashboard: การปกป้องความเป็นส่วนตัวของข้อมูล (Data Isolation & Zero Leakage) และการกระตุ้นให้ผู้ใช้เข้ามามีส่วนร่วม (Issue #62):**
    ในขั้นตอนของ **Issue #62** การออกแบบและพัฒนาแดชบอร์ดสำหรับ Requester สะท้อนหลักการออกแบบที่ให้ผู้ใช้เป็นศูนย์กลาง (User-Centric Design) ควบคู่กับมาตรฐานความปลอดภัยระดับสูงสุด:
    - **Strict Data Isolation (BR-16, AC-09, DASH-REQ-02):** ความปลอดภัยของข้อมูลเป็นสิ่งที่ไม่สามารถประนีประนอมได้ เซิร์ฟเวอร์บังคับใช้การคัดกรองระดับฐานข้อมูลผ่าน `requesterId = req.user.id` จากเซสชันจริง 100% ส่งผลให้ข้อมูลตัวชี้วัดและรายการตั๋วของผู้ใช้แต่ละคนถูกแยกขาดจากกันโดยเด็ดขาด ปราศจากข้อมูลรั่วไหล (Zero Leakage) โดยได้รับการพิสูจน์ผ่าน automated test `requester-dashboard.api.test.ts`
    - **Action-Oriented Dashboard Design (UI-DASH-02):** แดชบอร์ดของ Requester ไม่ควรเป็นเพียงแค่ตารางตัวเลขแห้ง ๆ แต่ต้องช่วยให้ผู้ใช้ทราบว่า **"มีอะไรที่ตนเองต้องทำบ้าง"** เราจึงออกแบบให้มีการ์ดเน้นพิเศษ "Action Needed (Waiting on You)" พร้อมกล่องเตือนสีเหลืองอำพัน (Attention Required Section) สำหรับตั๋วที่อยู่ในสถานะ `WAITING_FOR_REQUESTER` เพื่อให้ผู้ใช้สามารถคลิกเข้าไปให้ข้อมูลเพิ่มเติมแก่เจ้าหน้าที่ IT ได้ในทันที
    - **Clean Empty State Guidance:** ในกรณีที่ผู้ใช้เพิ่งเริ่มใช้งานหรือไม่มีตั๋วคงค้างในระบบ แดชบอร์ดจะไม่แสดงความว่างเปล่าที่น่าสับสน แต่จะแสดงกล่องข้อความต้อนรับและปุ่มทางลัด `+ Create a Ticket` เพื่อนำทางผู้ใช้ให้สามารถสร้างคำร้องขอความช่วยเหลือได้อย่างราบรื่น
    - **Full-Stack Regression Assurance:** การบูรณาการแดชบอร์ดเข้าสู่ Shell หน้าบ้านทั้งใน `AppHeader` และ `App.tsx` ได้รับการพิสูจน์ว่าไม่กระทบต่อการทำงานเดิม โดยชุดทดสอบทั้งฝั่ง Server (20 ไฟล์ 223 เทสต์) และฝั่ง Client (18 ไฟล์ 110 เทสต์) ผ่านครบ 100% รวม 333 การทดสอบโดยไม่มีข้อผิดพลาดใด ๆ

    - **Catching Runtime Import Bug via E2E Rendering:** ในระหว่างการรันสคริปต์แคปภาพหน้ารายละเอียดตั๋ว เราค้นพบข้อผิดพลาดรันไทม์ที่คอมไพเลอร์มองข้าม คือการลืมนำเข้า `StaffTicketDetail` ใน `App.tsx` ส่งผลให้หน้าเว็บแครชเมื่อเปิดดูตั๋ว การทำ Visual QA ในสภาพแวดล้อมเบราว์เซอร์จริงจึงมีคุณค่ามหาศาลในการดักจับข้อผิดพลาดก่อนถึงมือผู้ใช้งาน

12. **Playwright E2E Automation, Stateful Database Lifecycle Management, และ Full Regression Hardening (Issue #64):**
    ในขั้นตอนของ **Issue #64** การทำ End-to-End Testing บนเบราว์เซอร์จริงด้วย Playwright เป็นการพิสูจน์คุณค่าของการบูรณาการทั้งระบบ (System Integration) ตั้งแต่ส่วนต่อประสานผู้ใช้ (Frontend React), การสื่อสารผ่านระบบเครือข่ายและ API (REST/HTTP), กลไกการยืนยันตัวตนและการกักกันสิทธิ์ (Authentication & RBAC), ไปจนถึงกฎทางธุรกิจและการจัดเก็บข้อมูลจริงในฐานข้อมูล PostgreSQL:
    - **Resolution Gate End-to-End Enforcement (E2E-02):** การทดสอบในสภาพแวดล้อมจริงยืนยันว่า Resolution Gate ทำงานได้อย่างสมบูรณ์แบบ ทั้งบน UI ที่ปิดการใช้งานปุ่มและแสดงคำเตือนสีเหลืองอำพัน และในระดับ API ที่ส่งกลับ 400 Bad Request เมื่อมีการพยายามข้ามการตรวจสอบ พร้อมทั้งยืนยันว่าการที่ Requester ระบุ Problem Appears Resolved จะเป็นเพียงสัญญาณแนะนำให้เจ้าหน้าที่ IT ตรวจสอบเท่านั้น โดยสถานะตั๋วยังคงเป็น IN_PROGRESS ไม่ถูกเปลี่ยนเป็น RESOLVED โดยพลการ
    - **Role Dashboards & Interactive Drill-Down Verification (E2E-03):** การทดสอบยืนยันว่าแดชบอร์ดของทั้งสองบทบาทแสดงตัวเลขตัวชี้วัดที่ถูกต้อง และเมื่อคลิกไปยังการ์ดต่าง ๆ สามารถนำทาง (Drill-down) ไปยังคิวงานหรือหน้ารายการตั๋วพร้อมฟิลเตอร์ที่ถูกต้องได้อย่างไร้รอยต่อ รวมถึงยืนยันว่า Requester ไม่สามารถยิงเรียก API แดชบอร์ดของเจ้าหน้าที่ IT ได้ (403 Forbidden)
    - **Stateful Test Lifecycle & Deterministic Database Seeding:** การรัน E2E ควบคู่กับ Integration Tests บนฐานข้อมูลเดียวกันสอนบทเรียนสำคัญเรื่อง State Leakage: การที่ E2E สร้างหรือลบข้อมูลในตั๋วทดสอบ (TKT-2026-000001 ถึง 000003) อาจส่งผลกระทบต่อ seed tests ของเซิร์ฟเวอร์ได้หากไม่มีการคืนค่า เราจึงปรับปรุง seed.ts และการทำความสะอาดฐานข้อมูลให้มีความเป็น Deterministic อย่างแท้จริง เพื่อให้ทุกชุดทดสอบสามารถรันซ้ำได้อย่างอิสระและได้ผลลัพธ์ที่สม่ำเสมอ
    - **Zero Regression Across Labs 1–4:** ผลลัพธ์จากการรันชุดทดสอบเต็มรูปแบบ (Full Regression Suite) ครบทั้ง 377 การทดสอบ (Server 223/223, Client 116/116, E2E 38/38) ผ่านครบ 100% ยืนยันว่าการต่อเติมฟีเจอร์ใหม่ใน Lab 4 ไม่ได้ทำให้ฟังก์ชันเดิมใด ๆ ของ Lab 1, 2, และ 3 เกิดความเสียหายหรือพฤติกรรมถดถอยแม้แต่รายการเดียว
