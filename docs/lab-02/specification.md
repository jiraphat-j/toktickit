# Lab 2 Sprint Engineering Specification
### TokTickIT — Requester Ticketing MVP with UI Foundation

---

## 1. Sprint Goal

Deliver a working Requester-facing ticketing experience: a Requester (selected through a temporary
Development Requester selector) can create an IT support ticket with supporting attachments, receive a
system-generated Ticket Number, browse and search their own tickets in My Tickets, open a read-only Ticket
Detail screen, and manage their own attachments through soft removal — all on a consistent, responsive
Zen Green UI, with ownership strictly enforced so no Requester can see another Requester's data.

## 2. Stakeholder Request Interpretation

IT wants a self-service intake channel for support requests. Because real login is not ready yet, the sprint
uses a seeded "Development Requester" identity to simulate per-user ownership. A Requester must describe a
problem, classify it, attach evidence, and submit it; afterwards they must be able to find, filter, and inspect
their own tickets and attachments, but never another Requester's. The sprint should also establish the shared
visual language (Zen Green) and reusable UI conventions (forms, badges, list states) that later sprints build on.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity switch)
- Create Ticket (form, validation, attachments, success/failure states)
- My Tickets (search, filter, sort, pagination, empty/no-results states)
- Requester Ticket Detail (read-only)
- Attachment lifecycle: add, download, soft-remove
- Ownership enforcement across all Requester-facing APIs
- Zen Green UI foundation: shell, nav, forms, badges, responsive rules

### Excluded
- Real authentication (login, passwords, sessions, tokens, roles)
- IT Staff dashboard/queue, ticket claiming, IT Priority changes, Ticket Owner assignment
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond the initial `NEW` status (no resolve/close/reopen)
- Administrator functions (user/role/reference-data management)

| FR-03 | The system shall let the Requester view a paginated list of only their own tickets in My Tickets. |
| FR-04 | The system shall let the Requester search their tickets by Ticket Number or Summary. |
| FR-05 | The system shall let the Requester filter the ticket list by Category, Requested Priority, and Current Status. |
| FR-06 | The system shall let the Requester sort the ticket list by Created Date, Last Updated, or Ticket Number. |
| FR-07 | The system shall let the Requester open a read-only Ticket Detail screen for tickets they own. |
| FR-08 | The system shall let the Requester add a permitted attachment to an existing owned ticket. |
| FR-09 | The system shall let the Requester download an active (non-removed) attachment. |
| FR-10 | The system shall let the Requester soft-remove an attachment they added, with a required reason. |
| FR-11 | The system shall present a Development Requester Selection screen before any ticket-related screen is used. |
| FR-12 | The system shall persist the selected Development Requester as the current context and scope all subsequent data to it. |

| FR-14 | The system shall exclude inactive Development Requesters from the selector. |
| FR-15 | The system shall present distinguishable loading, empty, no-results, validation-error, and server-error states on Create Ticket, My Tickets, and Ticket Detail. |

## 5. Business Rules

| ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend as `TKT-{creationYear}-{6-digit zero-padded global sequence}` and is globally unique. |
| BR-02 | A new Ticket always begins with Current Status `NEW`; the client cannot set status at creation. |
| BR-03 | The Development Requester selector is a Lab 2 testing mechanism only and is never treated as authentication. |
| BR-04 | Only Development Requesters with `isActive = true` appear in the selector dropdown. |
| BR-05 | The backend independently validates the requester context on every requester-scoped call; an inactive or unknown requester id is rejected. |
| BR-06 | Switching the Development Requester immediately clears and reloads all requester-scoped views — no stale data from the previous requester is shown. |
| BR-07 | A Ticket belongs to exactly one Requester, fixed at creation time, and ownership never changes afterward. |
| BR-08 | A Requester may only view, list, or manage Tickets and Attachments for which they are the owning Requester. |
| BR-09 | Accessing a Ticket or Attachment owned by a different Requester returns `404 Not Found` (not `403`), so ticket existence is never revealed to a non-owner. |
| BR-10 | Category, Related System, Summary, Description, and Requested Priority are required; Ticket Number and Ticket Date are system-generated and read-only. `Ticket Date` is the Ticket's `createdAt` value shown in the Requester's local display format. |
| BR-11 | Ticket Summary must be 5–150 characters after trimming leading/trailing whitespace. |
| BR-12 | Ticket Description must be 10–2000 characters after trimming; whitespace-only input counts as empty. |
| BR-13 | The Submit button is disabled and shows a busy state for the duration of the create-ticket request. |
| BR-14 | The client sends one UUID in the `Idempotency-Key` header per create-form attempt. The backend stores the key and request fingerprint atomically for 24 hours: a repeated identical request returns the original Ticket, while reuse with different content returns `409 Conflict`. |
| BR-15 | If ticket creation fails validation or the server is unreachable, all entered field values remain in the form and a clear error is shown. |
| BR-16 | If the Ticket is created but a supporting attachment upload fails, the Ticket is **not** rolled back; the Requester sees a partial-success message and can retry the attachment from Ticket Detail. |
| BR-17 | Allowed attachment types are JPG, JPEG, PNG, WEBP, and PDF. The backend validates an allowlisted extension, claimed MIME type, and file signature where supported; it never trusts the browser-supplied MIME type alone. |
| BR-18 | Maximum attachment size is 5 MB per file. |
| BR-19 | A Ticket may have at most 5 **active** (non-removed) attachments; removed attachments do not count toward this limit. |
| BR-20 | Attachment removal is a soft removal — the record is flagged removed with a timestamp and reason, never physically deleted. |
| BR-21 | Removing an attachment requires a non-empty reason (minimum 3 characters) and an explicit confirmation step. |
| BR-22 | A removed Attachment remains visible as metadata only (filename, size, upload date, removal date) but cannot be downloaded or previewed. |
| BR-23 | Only the owning Requester may add or remove attachments on their own ticket. |
| BR-24 | My Tickets search matches Ticket Number or Summary, case-insensitively, by partial match. |
| BR-25 | My Tickets filters (Category, Requested Priority, Current Status) combine with AND logic. |
| BR-26 | My Tickets supports sorting by Created Date, Last Updated, or Ticket Number, ascending or descending; the default is `createdAt DESC, id DESC`, where `id DESC` is the stable secondary sort. |
| BR-27 | My Tickets pagination defaults to 8 items/page (allowed sizes: 8, 20, 50). An out-of-range positive page returns an empty page with valid metadata; non-integer, zero, negative, unsupported page size, sort field, or sort direction values return `400 Bad Request`. |
| BR-28 | The Empty state (Requester has zero tickets ever) is visually and textually distinct from the No-Results state (a search/filter matched zero existing tickets). |
| BR-29 | Category/Related System dropdowns show only active records; a Ticket referencing a since-deactivated Category or Related System still displays that name correctly on Ticket Detail. |
| BR-30 | The Development Requester identity travels from client to backend via an `X-Dev-Requester-Id` header, not an auth token. `requesterId` is never accepted in a create-ticket request body. Lab 3 replaces this header with a server-derived session identity without changing the ownership schema. |
| BR-31 | The selected Development Requester id is stored in `sessionStorage` under `toktickit.devRequesterId`. On reload, the client revalidates it against the active-requester API; if absent, invalid, inactive, or unavailable, ticket screens return to the selector with a safe message. |
| BR-32 | Attachment storage uses a server-generated opaque storage key, never the original filename as a path. Download uses the original filename only in a safe `Content-Disposition` response. |
| BR-33 | A seed run is idempotent: it upserts reference data and Development Requesters by their unique name/email keys and never creates duplicates. It creates the required Categories, at least six Related Systems, at least four active Development Requesters, and at least one inactive Development Requester. |
| BR-34 | Lab 2 only creates and seeds Tickets with Current Status `NEW`; future status values may be added in a later migration but are not seeded, displayed as workflow choices, or written by Lab 2 APIs. |

## 7. Data Changes

Concepts: `DevRequester`, `Category`, `RelatedSystem`, `Ticket`, `Attachment`, and `TicketCreationRequest`
(the 24-hour idempotency record for a successful create request).

`Ticket Date` in the UI/API is the Ticket's immutable `createdAt` timestamp; no duplicate date column is stored.

```prisma
enum Priority {
  LOW
  MEDIUM
  HIGH
}

enum TicketStatus {
  NEW
}

model DevRequester {
  id        Int      @id @default(autoincrement())
  fullName  String
  email     String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  tickets   Ticket[]
  ticketCreationRequests TicketCreationRequest[]

  @@index([isActive])
}

model Category {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  tickets   Ticket[]

  @@index([isActive])
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  tickets   Ticket[]

  @@index([isActive])
}

model Ticket {
  id                Int           @id @default(autoincrement())
  ticketNumber      String        @unique
  requesterId       Int
  requester         DevRequester  @relation(fields: [requesterId], references: [id])
  categoryId        Int
  category          Category      @relation(fields: [categoryId], references: [id])
  relatedSystemId   Int
  relatedSystem     RelatedSystem @relation(fields: [relatedSystemId], references: [id])
  summary           String
  description       String
  requestedPriority Priority
  itPriority        Priority?
  currentStatus     TicketStatus  @default(NEW)
  createdAt         DateTime      @default(now())
  updatedAt         DateTime      @updatedAt
  attachments       Attachment[]
  creationRequest   TicketCreationRequest?

  @@index([requesterId, createdAt])
  @@index([requesterId, updatedAt])
  @@index([currentStatus])
  @@index([categoryId])
  @@index([createdAt])
}

model Attachment {
  id               Int       @id @default(autoincrement())
  ticketId         Int
  ticket           Ticket    @relation(fields: [ticketId], references: [id])
  originalFileName String
  storedFileName   String    @unique
  mimeType         String
  sizeBytes        Int
  uploadedAt       DateTime  @default(now())
  isRemoved        Boolean   @default(false)
  removedAt        DateTime?
  removedReason    String?

  @@index([ticketId])
}

model TicketCreationRequest {
  id                 String       @id // value from Idempotency-Key
  requesterId        Int
  requester          DevRequester @relation(fields: [requesterId], references: [id])
  requestFingerprint String
  ticketId           Int          @unique
  ticket             Ticket       @relation(fields: [ticketId], references: [id])
  createdAt          DateTime     @default(now())
  expiresAt          DateTime

  @@index([expiresAt])
}
```

**Migration notes:** `ticketOwnerId` (IT Staff assignment) is intentionally **not** added yet — it belongs to
the IT Staff workflow, which is out of scope for Lab 2, and will be introduced with the staff `User` model in a
later lab. `TicketStatus` contains only `NEW` in Lab 2; later lifecycle values are deliberately deferred rather
than seeded or exposed early. The requester-scoped composite indexes support the primary My Tickets queries:
ownership scope followed by Created Date or Last Updated sorting.

`TicketCreationRequest` makes successful ticket creation idempotent. Its primary key is the UUID supplied in
`Idempotency-Key`; it records the owning requester, a request fingerprint, the one created Ticket, and expiry.
Expired records are ignored and may be deleted by a documented cleanup task.

### 7.1 Required Seed Data

The Prisma seed uses upserts and can be run repeatedly without duplicates. It includes:

- Categories: `Account and Access`, `Hardware`, `Software`, and `Network`.
- Related Systems: `Email`, `Campus Wi-Fi`, `VPN`, `LEB2 App`, `Grade Submission App`, `Printer`, and `Corporate Laptop`.
- At least four active Development Requesters: [names/emails to be finalised in `prisma/seed.ts`].
- At least one inactive Development Requester, excluded from the selector.

The seed may create `NEW` Tickets for search, filter, sort, and pagination evidence, but it must not seed later
ticket statuses.

## 8. API Contract

Full detail lives in `api-spec.md`. Summary of endpoints:

| Capability | Method & Path |
|---|---|
| List active Development Requesters | `GET /api/dev-requesters` |
| List active Categories | `GET /api/categories` |

All requester-scoped endpoints require `X-Dev-Requester-Id`; reference-data endpoints do not. The detailed

`docs/lab-02/api-spec.md` and must remain consistent with these rules.

## 9. Acceptance Criteria

**Create Ticket**
- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02** Given the Summary field is empty, when the Requester submits, then an inline message appears under Summary and the create-ticket API is not called.
- **AC-03** Given the Description exceeds 2000 characters, when the Requester submits, then an inline message appears under Description and submission is blocked.
- **AC-04** Given the Submit button has been clicked, when the request is in flight, then the button shows a busy state and is disabled.
- **AC-05** Given the same idempotency key is sent twice (double-click or retry), when both requests reach the backend, then only one Ticket is created.
- **AC-06** Given the backend is unreachable, when the Requester submits a valid Ticket, then a safe error message is shown and every entered field value remains in the form.
- **AC-07** Given the Ticket is created successfully but the attachment upload fails, then the Ticket still exists and a partial-success message with a retry option is shown.

**Attachments**
- **AC-08** Given a JPG under 5 MB, when attached during creation, then it appears in the created Ticket's attachment list.
- **AC-09** Given a file type outside JPG/JPEG/PNG/WEBP/PDF, when selected, then it is rejected with a clear message and never uploaded.
- **AC-10** Given a file over 5 MB, when selected, then it is rejected with a size-limit message.
- **AC-11** Given a Ticket already has 5 active attachments, when a 6th is attempted, then the upload is blocked with a limit-reached message.
- **AC-12** Given an active attachment, when the Requester clicks Download, then the file downloads successfully.
- **AC-13** Given Remove is confirmed without a reason, then the removal is blocked until a reason is entered.
- **AC-14** Given a valid reason is entered and removal confirmed, then the attachment is marked removed, its metadata stays visible, and download/preview is disabled.
- **AC-15** Given a Ticket has one active and one soft-removed attachment, when a new attachment is added, then the upload succeeds because only active attachments count toward the limit of 5.

**My Tickets**
- **AC-16** Given a Requester searches "laptop", then only Tickets whose number or summary contains "laptop" (case-insensitive) are shown.
- **AC-17** Given Category=Hardware and Current Status=Open are both applied, then only Tickets matching both are shown.
- **AC-18** Given more Tickets exist than one page holds, when going to page 2, then the next set loads and pagination reflects page 2 correctly.
- **AC-19** Given a Requester has zero Tickets ever, when opening My Tickets, then a distinct "no tickets yet" empty state is shown.
- **AC-20** Given a search/filter combination matches none of the Requester's tickets, then a distinct "no results" state with a Clear Filters action is shown.

**Ownership & Ticket Detail**
- **AC-21** Given a Requester opens Ticket Detail for a ticket they own, then all required fields render as read-only.
- **AC-22** Given Requester B is selected, when a Ticket belonging to Requester A is requested (list or detail), then it is not returned and a `404` is given.
- **AC-23** Given Requester A switches to Requester B, when My Tickets reloads, then Requester A's tickets are no longer visible.

**Development Requester Selector**
- **AC-24** Given no Development Requester is selected, when opening My Tickets/Create Ticket/Ticket Detail, then the Requester Selection screen is shown instead.
- **AC-25** Given no active Development Requesters exist, when the Selection screen loads, then an empty-state message is shown instead of a blank dropdown.
- **AC-26** Given the requester-list API call fails, when the Selection screen loads, then a safe error state with Retry is shown.
- **AC-27** Given an inactive Requester's id is sent directly to any requester-scoped API, then the backend rejects it with `400 Bad Request`.

**Responsive & Accessibility**
- **AC-28** Given a mobile viewport (<768px), when Create Ticket/My Tickets/Ticket Detail are opened, then fields stack vertically, buttons stay tappable, and no horizontal scrolling occurs.
- **AC-29** Given a tablet viewport (768–991px), then a two-column layout is used where practical and Summary/Description retain adequate width.
- **AC-30** Given a keyboard-only user tabs through Create Ticket, then every control is reachable in a logical order with a visible focus indicator.
- **AC-31** Given the selector or Create Ticket form loads, when reference data is active, then only active Development Requesters, Categories, and Related Systems are offered; an inactive Requester is absent from the selector.
- **AC-32** Given an Attachment has been soft-removed, when any Requester calls its download or preview endpoint directly, then the backend returns `404` and no file content is returned.
- **AC-33** Given a Ticket-list query has an invalid page, page size, sort field, or sort direction, when it is submitted, then the API returns a safe `400` error; an out-of-range positive page returns an empty page with valid metadata.
- **AC-34** Given Requester B is selected, when B attempts to upload, remove, or download an Attachment belonging to Requester A, then the operation returns `404` and does not change Attachment data.
- **AC-35** Given a Requester is selected, when the application is refreshed, then the stored context is revalidated and displayed; if it is missing or invalid, the selector is shown instead.
- **AC-36** Given two valid create requests arrive concurrently, when each has a different idempotency key, then two Tickets receive distinct official Ticket Numbers; when they use the same key and payload, exactly one Ticket is created.

## 11. Assumptions and Decisions

- **Ticket Number format** — `TKT-{year}-{6-digit sequence}`, using a dedicated PostgreSQL sequence read atomically in the Ticket-creation transaction. The sequence is global (not reset yearly); the year is cosmetic and comes from `createdAt`.
- **404 over 403 for ownership failures** — chosen to avoid confirming a ticket ID exists to a non-owner
  (information-disclosure hardening), even though Lab 2 has no real authentication yet.
- **Idempotency key** — a client-generated UUID sent in the `Idempotency-Key` header per create attempt. The
backend stores it with a request fingerprint for 24 hours; an identical retry returns the original Ticket, while
a key reused with different content returns `409 Conflict`.
- **Attachment slot freeing** — soft-removed attachments free up a slot; the 5-item cap applies to *active*
  attachments only, matching the spirit of "maximum active attachments" in the handout.
- **Requester context transport** — a plain header (`X-Dev-Requester-Id`) rather than a cookie/token, to keep
the mechanism obviously non-authenticating and easy to swap out in Lab 3. The selected id is kept in
`sessionStorage` and is always revalidated by the backend.
- **Attachment safety** — `5 MB` means `5 * 1024 * 1024` bytes. The server stores a generated opaque key,
not an original filename/path; the original filename is metadata used only for a safely encoded download name.
- **List-query validation** — malformed query parameters fail with `400`; a valid page number beyond the final
page succeeds with an empty `items` array and complete pagination metadata.
- **`itPriority` and `ticketOwnerId`** — `itPriority` exists in the schema (nullable) since it's shown on the
  illustrative screen, but nothing in Lab 2 sets it; `ticketOwnerId` is deferred entirely to the lab that
  introduces the IT Staff `User` model, to avoid a dangling/unused FK now.
- **Status lifecycle deferral** — `TicketStatus` contains only `NEW` in Lab 2. A later lab may add lifecycle
  values through its own migration, rather than exposing out-of-scope workflow states now.
